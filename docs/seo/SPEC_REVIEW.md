Make a separate website checkout from an identified commit, record its remote/branch/SHA, inspect its own instructions and deployment files, and confirm the live URL inventory against it. Preserve current CRM changes, including `package.json`, `.nvmrc`, and `.DS_Store`. These prerequisites can proceed without waiting for account access.

**R2 — Specify and verify the lead contract before frontend or server rewrites.** T6 describes required fields but not the complete deployed contract. Read the website proxy and current CRM route to record method, allowed `formType` values, field names, validation bounds, success semantics, timeout behavior, and secret handling. Test against a fake upstream: success, non-2xx JSON, non-JSON error, timeout, unavailable upstream, invalid input, duplicate click, and missing configuration. Public errors must never echo upstream bodies, credentials, or personal data. A local mock pass must be reported separately from real CRM delivery verification.

## High-priority revisions

**R3 — Make analytics privacy testable.** Allowlisting a UTM key does not make its value safe: `utm_campaign` can still contain an email or arbitrary text. Limit capture to needed source/medium/campaign fields, sanitize values and omit suspect values; omit `utm_term`/`utm_content` by default. Use only known website pathnames for analytics page locations and strip the entire query and fragment. Disable automatic page views/enhanced events until their payloads are verified; sanitize referrer explicitly. State the activation/consent behavior and storage duration. Analytics disabled by default must make no provider request and create no analytics storage. Test payloads using deliberately sensitive-looking query values and inspect browser requests after test configuration. Never label attribution as anonymous simply because form fields were excluded.

**R4 — Define publication migration, timezone, and build cleanup.** One article is already publicly accessible despite a future date. Inventory and explicitly record any currently live URL intentionally withdrawn; do not quietly remove it as a build side effect. Preserve already published, fact-checked content where an accurate date can be established; genuinely scheduled material stays absent until release. Choose `America/Chicago` for date-only release boundaries, define missing/invalid date behavior, and reject inconsistent `dateModified < datePublished` metadata. Clean the output directory before every build so previously generated future pages cannot survive. Test builds before/on/after the release boundary, stale output removal, article lists, related links, and sitemap together. Publication automation must not create inaccurate dates.

**R5 — Make proxy/redirect behavior deployment-safe.** Document the actual Railway start/build commands, Node version, public directory, health check, and upstream proxy behavior before replacing server code. Exempt API POST requests and health checks from host redirects that could break lead delivery. Test forwarded-header spoofing, HTTPS loops, HEAD, malformed paths, directory traversal, and direct requests for `.env`, `.git`, source files, tests, and package files. Do not enable a production redirect until the destination domain and TLS work. Treat compression and caching changes as optional if the deployed platform already supplies correct behavior; measure before broadening the server rewrite.

**R6 — Tighten editorial scope and proof handling.** The 31-article review must explicitly include unsafe roof-access/DIY advice, unsupported guarantees, deductible-waiver wording, storm availability, and claims about financing or warranties. Validate legal/permit/insurance claims against current primary sources at implementation time, rather than relying solely on the dated audit. Also inspect Home/About/service pages and visible testimonials, captions, alt text, and JSON-LD for unsupported claims. Do not imply existing images prove a named city, date, material, or customer project unless their provenance supports it. A prepared case-study template and missing evidence are separate deliverables; they do not equal completed case studies.

**R7 — Add a release and rollback gate.** Record the website service/repo/environment identity, previous deployed commit, candidate commit, deployment mechanism, required environment variable names, and rollback procedure before production release. Do not print variable values. First validate the built artifact, then test a candidate environment when available. Preserve existing service routes and CRM compatibility. If deployment or DNS access is absent, deliver the complete reviewable website branch/PR plus exact access-dependent steps; do not describe a local build as deployed. After release, verify representative new and existing URLs, redirects, robots/sitemap, assets, and health without creating real leads. Revert if content delivery or lead proxy compatibility regresses.

## Medium-priority revisions

**R8 — Make before/after reporting comparable.** Save machine-readable baseline and final results using the same URL sample, viewport, runtime, network conditions, and audit rules. Give original-page coverage and new-page coverage separately; explicitly account for withheld pages. Lighthouse, if available, should include SEO/accessibility/performance as separate metrics and representative homepage, service, contact, and article templates. Record unavailable tooling rather than inventing scores. Custom structural checks should list counts and failures, not be presented as a Google SEO score.

**R9 — Make parallel editing boundaries concrete.** Agents share a filesystem. Assign exact paths and reserve global build/server/JS/CSS/data files for their owners. Establish a page/body markup contract before the content agents edit pages. Require the technical agent to read current source at build time, rather than overwriting bodies from an earlier copy. Integration should review diffs for lost copy, duplicate headers/forms/schema, missing anchors, and absent navigation entries. Serialize lockfile/package edits and parent integration.

**R10 — Make backlink work a useful handoff without invented outcomes.** The matrix should include direct eligibility/application/pricing pages checked on the research date, costs marked confirmed versus quote required, account/verification dependencies, and a ranked first-five action list. Separate free owned profiles, earned editorial opportunities, and paid memberships/sponsorships. Add duplicate-listing checks and a canonical website URL to the listing packet. Sponsorships should have legitimate audience value independent of ranking; do not promise followed links. Record opportunities researched, profiles actually updated, links verified live, and referral results as separate statuses. No fixed number of links can establish that the site has “sufficient backlinks.”
